# Сессия

Сессия EPP — это TLS-соединение, поверх которого выполнен вход. Эта страница охватывает всё от
сокета до выхода: настройку клиента, проверку сертификата сервера, открытие и закрытие сессии, смену
пароля, чтение предупреждений безопасности от сервера и запись кадров в журнал без утечки учётных
данных.

Форма её никогда не меняется:

```
connect()  →  <greeting>  →  login()  →  commands …  →  logout()  →  disconnect()
```

`connect()` открывает сокет и читает приветствие. `login()` выполняет аутентификацию. Идут команды.
`logout()` завершает сессию на стороне реестра, а `disconnect()` закрывает сокет.

## Config

`com.epptools.sdk.Config` хранит настройки соединения. Создаётся он через `Config.builder()`, который
берёт три обязательных значения, а всем остальным полям подставляет значения по умолчанию:

```java
import com.epptools.sdk.Config;

Config config = Config.builder("epp.registry.example", "EXAMPLE", System.getenv("EPP_PASSWORD"))
        .caFile("/etc/epp/registry-ca.pem")
        .build();
```

Опечатке здесь взяться негде: у каждого поля свой метод билдера, а несуществующего метода ваш
редактор не даст набрать. Поля объявлены публичными и неизменяемыми, так что всё, что вы не
передали, можно прочитать прямо с объекта.

### Все поля

| Поле | По умолчанию | Что это и что будет, если задать неверно |
|---|---|---|
| `host` | обязателен | Имя хоста реестра. Пустое вызывает `ConfigException` из `build()`. Это же имя передаётся в TLS для SNI и для проверки имени узла, поэтому IP-адрес здесь не пройдёт проверку имени против сертификата, выпущенного на имя хоста. |
| `clid` | обязателен | Ваш идентификатор регистратора: 3–16 символов из латинских букв, цифр и дефиса. Пустой вызывает `ConfigException` из `build()`. Правильное по форме, но неверное значение сервер отклоняет кодом 2200. |
| `password` | обязателен | Ваш EPP-пароль. Пустой вызывает `ConfigException` из `login()`. Короче 6 символов или длиннее 128 — тоже `ConfigException`, ещё до открытия сокета. Длиннее 16 возможен только там, где сервер предлагает RFC 8807, — см. [Длинные пароли](#длинные-пароли) ниже. |
| `port` | `700` | Порт EPP. Меняйте его, только если вам выдали другую точку подключения. Неверный порт даёт `ConnectionException` из `connect()`. |
| `lang` | `"en"` | Язык сообщений о результате от сервера в этой сессии. Приветствие перечисляет языки, которые предлагает сервер; значение, которого он не предлагает, валит вход кодом 2102. Это язык `message()`, а не poll-уведомлений: те несут собственный. |
| `connectTimeout` | `10.0` | Сколько секунд ждать TCP-соединения и рукопожатия TLS. Слишком малое значение на медленном канале даёт `ConnectionException`, который читается как отказ в соединении. |
| `readTimeout` | `30.0` | Сколько секунд ждать кадр ответа. Дробные значения учитываются (`2.5` — две с половиной секунды). Ноль или меньше поднимается до одной секунды, так что «ждать вечно» это никогда не означает. Чтение, вышедшее за тайм-аут, выбрасывает `ConnectionException` и **закрывает соединение**: недочитанный кадр оставляет поток байтов на неизвестном смещении, и следующая команда прочитала бы середину ответа на эту. |
| `verifyPeer` | `true` | Проверять цепочку сертификата сервера. Оставьте включённым. См. [TLS](#tls-и-проверка-сертификата). |
| `verifyPeerName` | `true` | Проверять, что сертификат соответствует `host`. Отключение — узкое послабление (сертификат тот, имя хоста не то), которое иногда оправдано при разработке. |
| `caFile` | `null` | Путь к PEM-связке CA, подписавшего сертификат **сервера**. Нужен против точки подключения, которая использует собственный закрытый CA реестра, чьего сертификата нет ни в одном хранилище доверия. Не задан или указан неверно — рукопожатие падает с ошибкой проверки. Без `caFile` клиент доверяет хранилищу самого JDK, и это верно для сертификата, которому доверяют браузеры. |
| `clientCert` | `null` | Путь к **вашему** клиентскому сертификату, PEM. Нужен, только если ваша точка подключения требует взаимного TLS. |
| `clientKey` | `null` | Путь к вашему закрытому ключу, PEM в формате PKCS#8. Можно не указывать, если ключ вложен в `clientCert`. |
| `clientKeyPassphrase` | `null` | Парольная фраза для зашифрованного клиентского ключа. Неверная — и рукопожатие падает на загрузке ключа, а не на проверке узла. |
| `objUris` | `null` | Объектные сервисы, которые объявлять в `<login>`. `null` означает «ровно то, что предложило приветствие», — поэтому сессию с настройками по умолчанию никогда не отклоняют из-за неподдерживаемого сервиса; **пустой список означает то же самое** — `epp-1.0.xsd` требует хотя бы один `objURI`, так что уважить пустому значило бы собрать вход, который отклонят сразу. Задайте своё значение — и любой URI, который этот сервер не обслуживает, завалит вход кодом 2307. Базовый URI `epp-1.0` никогда не отправляется как объектный сервис, перечислен он в приветствии или нет. |
| `extUris` | `null` | Сервисы расширений, которые объявлять. `null` означает «ровно то, что предложило приветствие», как и для `objUris`, — но **пустой список здесь не объявляет ничего**, и это легитимно: `svcExtension` сам по себе необязателен, так что именно так просят чистую RFC-сессию. Объявить меньше расширений, чем вы используете, — значит не получить от реестра данные этого расширения. |
| `clTRIDPrefix` | `"JAVA-SDK"` | Первый сегмент каждого автоматически создаваемого клиентского идентификатора транзакции. Задайте в нём что-то, по чему ваша система узнаётся в записях реестра. См. [Команды](commands.md#клиентские-идентификаторы-транзакций). |
| `registryExtUri` | `null` | Пространство имён **собственного** объектного расширения этого реестра. `null` — обычный случай — означает «прочитать его из приветствия». Задавайте вручную только для реестра, чьё расширение названо не по образцу `…/registry-<версия>`, по которому идёт определение. Неверное значение не отвергается: расширение в неизвестном серверу пространстве имён ИГНОРИРУЕТСЯ, поэтому данные молча не доходят. См. [Команды](commands.md#собственные-расширения-вашего-реестра). |
| `registryBalanceUri` | `null` | То же самое для расширения баланса учётной записи. |
| `loginSecurity` | `true` | Участвовать в RFC 8807 там, где сервер его предлагает. Значение false лишает вас событий безопасности от сервера. См. [Безопасность входа](#безопасность-входа-rfc-8807). |

### `toString(): String`

Возвращает настройки соединения одной строкой. Полезно, когда рукопожатие не удалось и нужно
увидеть, с чем именно клиент его начинал:

```java
Config config = Config.builder("epp.registry.example", "EXAMPLE", "your-secret").build();

System.out.println(config);
// Config{host=epp.registry.example, clid=EXAMPLE, port=700, lang=en, verifyPeer=true, loginSecurity=true}
System.out.println(config.caFile);       // null — каждое поле публично и неизменяемо
```

**Пароля и парольной фразы ключа в этой строке нет** — намеренно, чтобы отладочный журнал их не
выдал. Сокет открывается только с **TLS 1.2 или TLS 1.3**: всё, что старше, отключается на самом
сокете, а не оставляется на усмотрение платформы. Проверка имени узла включается вместе с проверкой
цепочки, а `caFile`, `clientCert`, `clientKey` и `clientKeyPassphrase` применяются, только когда
задано соответствующее поле.

## TLS и проверка сертификата
| Сценарий | Настройка |
|---|---|
| Публичный сертификат, которому доверяет браузер | ничего — значения по умолчанию (`verifyPeer(true)`, `verifyPeerName(true)`) верны |
| Сертификат закрытого CA или самоподписанный | `caFile(...)` — PEM-связка CA, подписавшего сертификат **сервера** |
| Взаимный TLS (реестр требует клиентский сертификат) | `clientCert(...)` + `clientKey(...)` (+ `clientKeyPassphrase(...)`, если ключ зашифрован) |
| Несовпадение имени хоста при разработке | `verifyPeerName(false)` |

**Какой из них ваш — решает реестр, так что спросите у него.** Многие реестры предъявляют
обычный сертификат, которому доверяют браузеры, и тогда настраивать нечего: без `caFile` клиент
доверяет хранилищу самого JDK. Другие держат свой CA, чьего сертификата в этом хранилище нет,
и тогда `caFile` должен указывать на его связку, иначе рукопожатие падает.

Сама аутентификация — это clID и пароль внутри TLS. Клиентский сертификат нужен только там,
где реестр требует взаимного TLS, и многие реестры дополнительно ограничивают доступ
зарегистрированными адресами отправления — это политика, а не протокол.

Одно замечание именно про Java: `clientKey` читает блок `-----BEGIN PRIVATE KEY-----` (RSA или EC),
то есть PKCS#8. Более старая форма `BEGIN RSA PRIVATE KEY` — это PKCS#1, и JDK её не читает;
преобразуйте ключ один раз командой `openssl pkcs8 -topk8 -in registrar.key -out registrar.key.pem`.
Сертификат и ключ могут лежать в одном файле — тогда `clientKey` не задавайте, и файл цепочки будет
прочитан для обоих.

### Когда рукопожатие не удаётся
Самый частый сбой при первом запуске — проверка сертификата, и выглядит он так:

```
ConnectionException: TLS handshake with epp.registry.example:700 failed - PKIX path building failed:
sun.security.provider.certpath.SunCertPathBuilderException: unable to find valid certification path
to requested target
```

Исключение несёт причину, о которой сообщил JDK, а не общее «неизвестная ошибка», поэтому сначала
читайте хвост сообщения. Затем проверьте связку из командной строки:

```bash
openssl s_client -connect epp.registry.example:700 -CAfile /path/to/registry-ca.pem </dev/null
# "Verify return code: 0 (ok)" означает, что связка верна; что угодно другое — что нет.
```

Короткий список диагнозов, в том порядке, в каком их стоит проверять:

| Сообщение | Обычная причина |
|---|---|
| `PKIX path building failed` | `caFile` не задан или указывает не на ту связку |
| `No subject alternative DNS name matching …` / несовпадение имени | `host` отличается от имени в сертификате — IP-адрес или псевдоним |
| `Connection refused` / `Connection timed out` | не тот порт либо ваш адрес отправления не внесён в белый список на межсетевом экране |
| `no PRIVATE KEY block found in …` / `unsupported client key type` | неверный путь `clientCert` / `clientKey`, ключ не в PKCS#8 или неверная `clientKeyPassphrase` |

**Не хватайтесь за `verifyPeer(false)`.** Он подставляет менеджер доверия, который не проверяет
ничего: сообщение исчезнет, а вы останетесь отправлять свой clID, свой пароль и все коды трансфера
тому, кто ответит по этому адресу, — и узнать об этом будет неоткуда. Если рукопожатие не проходит
проверку, значит, связка не та: запросите у реестра актуальную. `verifyPeerName(false)` — более
узкое послабление, и при разработке оно иногда оправдано; `verifyPeer(false)` не оправдан нигде.

## Открытие сессии

### `new Client(Config config, Transport connection, Client.Logger logger)`

Создание клиента ничего не открывает. Второй аргумент подменяет транспорт (см.
[Транспорт](#транспорт)); третий подключает логгер. Есть и короткие формы — `new Client(config)` и
`new Client(config, connection)`, — а `null` в любом из двух последних аргументов означает «взять то,
что по умолчанию».

```java
Client client = new Client(config);
```

### `connect(): Response`

Открывает TLS-сокет и читает незапрошенное `<greeting>` сервера (RFC 5730 §2.4), возвращая его как
[`Response`](responses.md).

```java
Response greeting = client.connect();
greeting.serviceObjUris();   // namespaces of the objects this server manages
greeting.serviceExtUris();   // the extensions it supports
greeting.value("svID");      // its name
greeting.value("svDate");    // its clock, as its own string
```

**Одна вещь, которую он делать отказывается:** первый кадр, не являющийся приветствием,
вызывает `ConnectionException`. Принять вместо него что пришло значило бы позволить
случайному ответу или баннеру промежуточного узла сойти за перечень сервисов, и тогда вход
объявил бы сервисы, которых этот сервер не предлагает, потеряв при этом расширения,
которые он предлагает. Проверки `host` здесь нет: `build()` отказывает пустому значению, а
`Config` — единственный путь сюда, так что вторая такая проверка никогда бы не сработала, а
проверка, которая сработать не может, читается как защита, не доказывая ничего.

Вызов `connect()` на уже открытом соединении не переоткрывает сокет — он читает следующий кадр как
приветствие. Для этого используйте `hello()`.

### `greeting(): Response`

Последнее прочитанное приветствие или `null` до `connect()`. Помогает решить без обращения к
серверу, доступно ли расширение:

```java
import com.epptools.sdk.Namespaces;

Response greeting = client.greeting();
boolean fees = greeting != null && greeting.serviceExtUris().contains(Namespaces.FEE);
```

### `hello(): Response`

Отправляет `<hello>` и читает свежее `<greeting>`, которым отвечает сервер. Два применения:
перечитать меню сервисов и удержать простаивающую сессию — реестр закрывает сессию, которая
простояла слишком долго, а `hello` — самый дешёвый кадр, сбрасывающий этот отсчёт. Возвращённое
приветствие заменяет сохранённое.

### `login(): Response` и `login(String newPassword): Response`

Выполняет аутентификацию. Собирает `<login>` с вашими clID и паролем, `<version>1.0</version>`,
настроенным `<lang>` и перечнем сервисов — по умолчанию ровно тем, что предложило приветствие.

```java
Response response = client.login();
response.code();   // 1000
```

Если вызвать `login()`, не вызвав `connect()`, он сначала подключится.

Проверки, которые выполняются до сборки кадра, каждая — с `ConfigException`:

- пустой `clid` или `password`;
- пароль вне диапазона 6–128 символов;
- пароль длиннее 16 символов, когда этот сервер не объявляет RFC 8807: базовый элемент `<pw>` его не
  унесёт, а сервер ответил бы голым 2001, не назвав ни одного поля.

`AuthenticationException` выбрасывает только код 2200. Вход, отклонённый по любой другой причине,
приходит своим классом со своим способом лечения: 2502 (лимит сессий), 2501 (сервер закрывает
соединение), 2307 (сервис из `<svcs>` не предлагается), 2002 (на этом соединении уже выполнен вход),
2100 (версия протокола). Назвать их все ошибкой аутентификации — значит пойти менять пароль, который
был ни при чём. См. [Ошибки](errors.md).

### `Client.connectAndLogin(Config config): Client`

Статическое сокращение: создаёт клиент, подключается, входит и возвращает готовый клиент.

```java
try (Client client = Client.connectAndLogin(config)) {
    client.domain().info("example.com.ua");
    client.logout();
}
```

Он использует транспорт по умолчанию и не подключает логгер. Если нужно то или другое, пользуйтесь
конструктором.

### `isConnected(): boolean` и `isLoggedIn(): boolean`

`isConnected()` сообщает, открыт ли сокет. `isLoggedIn()` — удался ли вход и не выполнялись ли с тех
пор `logout()` или `disconnect()`.

Ни один из них не опрашивает сервер, поэтому сессия, которую реестр закрыл сам — по тайм-ауту
простоя, при перезапуске, — может ещё читаться как «вход выполнен», пока не упадёт следующая
команда. Относитесь к ним как к учёту у себя, а не как к проверке живости; проверка живости — это
`hello()`.

## Закрытие сессии

### `logout(): Response`

Отправляет `<logout>`. Сервер отвечает **1500** и закрывает связь. 1500 — код успеха, поэтому
исключения здесь не будет.

### `disconnect(): void` и `close(): void`

`disconnect()` закрывает сокет. Его безопасно вызывать, когда ничего не открыто, — поэтому его место
в `finally`. `close()` — то же самое под именем, которого требует `AutoCloseable`, так что `Client`
годится в ресурс try-with-resources:

```java
try (Client client = new Client(config)) {
    client.connect();
    client.login();
    // …
    client.logout();
}
```

Выход из блока закрывает сокет любым путём, включая брошенное исключение. Незакрытая сессия занимает
место в вашем лимите одновременных сессий, пока реестр не закроет её по тайм-ауту.

Тот же код, выписанный явно, — для клиента, чей срок жизни не укладывается в один блок:

```java
Client client = new Client(config);
try {
    client.connect();
    client.login();
    // …
    client.logout();
} finally {
    client.disconnect();
}
```

**Напишите один из двух.** У клиента нет никакой подстраховки на случай, если его просто забыли, —
в Java нет момента, в который её можно было бы надёжно выполнить: ни деструктора, ни
зарегистрированного финализатора. Клиент, который никто не закрыл, держит сокет открытым, а сессию —
занятой, пока реестр не закроет её по тайм-ауту. В долгоживущем процессе, хранящем клиент в поле или
в контейнере, это и есть та самая утечка мест в лимите сессий.

Обратите внимание: `close()` закрывает **сокет** и не отправляет `<logout>` — на этот момент кадру
может быть уже некуда идти. Реестр видит брошенное соединение, а не аккуратное завершение сессии,
поэтому писать нужно `logout()` по пути наружу, а try-with-resources оставить на все остальные пути.

## Смена пароля

Передайте новый пароль в `login()` — и он уйдёт как `<newPW>` рядом со старым, в том же кадре
(RFC 5730 §2.9.1.1). Изменение вступает в силу, только если вход удался.

```java
Response response = client.login("N3w-Secret-Pw");
// From here the session is authenticated. Every LATER session must use the new password.
```

Порядок здесь важен, потому что спросить у реестра, какой пароль действует, нельзя:

1. **Сначала** запишите новый пароль в своё хранилище секретов, пометив его как ожидающий.
2. Вызовите `login(newPassword)`.
3. При успехе сделайте его действующим. При неудаче действующим остаётся старый: реестр применяет
   изменение только при успешном входе.

Оба пароля проверяются на длину до открытия сокета. 6–16 символов — предел базовой схемы `<pw>`;
6–128 доступны там, где сервер предлагает RFC 8807, а смена **через** эту границу берётся на себя
библиотекой: при замене короткого пароля длинным переносится только новый.

### Длинные пароли
Пароль длиннее 16 символов не может ехать в базовом элементе `<pw>`. Там, где сервер объявляет
RFC 8807, библиотека отправляет в `<pw>` зарезервированный литерал `[LOGIN-SECURITY]`, а настоящий
пароль — в `<loginSec:pw>`; решение о литерале принимается **для каждого элемента отдельно**,
поэтому элемент, который всё ещё несёт собственное значение, никогда не утверждает, что его значение
лежит где-то ещё.

Два следствия, о которых стоит знать до того, как вы такой пароль зададите:

- Длинный пароль проходит аутентификацию только на точке подключения, которая предлагает это
  расширение. Любое ваше ПО, подключающееся к точке, которая его не предлагает, начнёт получать
  отказы в аутентификации.
- Поскольку литерал зарезервирован, `[LOGIN-SECURITY]` сам никогда не может быть паролем.

`Config.loginSecurity` этим не управляет. Перенесённый пароль отправляет блок в любом случае —
ехать ему больше не в чем.

## Безопасность входа (RFC 8807)
Там, где сервер предлагает расширение безопасности входа, вход несёт небольшой блок,
идентифицирующий этот клиент: имя и версию приложения, версию Java, семейство ОС, — а сервер отвечает
всем, что хочет видеть исправленным в этой сессии.

```java
for (Map<String, String> event : client.login().securityEvents()) {
    // type:  certificate | cipher | tlsProtocol | password | newPW | stat | custom
    // level: "warning" or "error"
    // text:  фраза, которую можно показать оператору
    alert(event.get("level"), event.get("type"), event.get("text"), event.get("exDate"));
}
```

`securityEvents()` возвращает `List<Map<String, String>>`. Каждая запись несёт `text`; `type`,
`name`, `level`, `exDate`, `value`, `duration` и `lang` появляются, когда событие их несёт, поэтому
обращение за тем, чего событие не прислало, даёт `null`. На здоровой сессии список пуст — считайте
любую запись поводом действовать.

| `type` | Когда возникает |
|---|---|
| `certificate` | ваш клиентский сертификат скоро истекает; `exDate` содержит точный момент |
| `tlsProtocol` | сессия согласовала устаревшую версию TLS; `name` содержит её |
| `cipher` | сессия согласовала набор шифров, не являющийся AEAD; `name` содержит его |
| `password` / `newPW` | что-то о самих учётных данных — например, длина, ограничивающая места, где их можно использовать |
| `stat` | статистика сессии, которую сервер хочет вам показать |
| `custom` | специфично для сервера; `name` его идентифицирует |

Сервер отправляет их только клиенту, который **участвовал** в расширении, потому что объявление URI
не является свидетельством его поддержки: многие клиенты формируют `<svcExtension>`, просто возвращая
содержимое приветствия. Поэтому блок уходит даже тогда, когда везти в нём нечего.

Поставьте в конфигурации `loginSecurity(false)`, чтобы остаться в стороне от расширения. Тогда вы не
получаете событий безопасности, а самое частое из них — клиентский сертификат на подходе к дате
истечения: альтернатива узнать о нём здесь — узнать утром, когда он перестанет работать.

Версия клиента, отправляемая в блоке, — это то, что содержит `Version.VERSION` в установленной вами копии.
Указывайте её в обращении в поддержку.

## Журналирование

`Client.Logger` — это три метода и ни одной зависимости, поэтому он оборачивает то, чем ваше
приложение пользуется и так.

```java
Client.Logger logger = new Client.Logger() {
    @Override public void debug(String message)   { System.err.println("[debug] " + message); }
    @Override public void info(String message)    { System.err.println("[info]  " + message); }
    @Override public void warning(String message) { System.err.println("[warn]  " + message); }
};

Client client = new Client(config, null, logger);
// или позже, а null — чтобы отцепить:
client.setLogger(logger);
```

Поверх фасада журналирования все три тела — по одной строке: `log.debug(message)`,
`log.info(message)`, `log.warn(message)`. Ради этого интерфейс и существует вместо зависимости от
какого-то одного из них.

Что пишется:

| Уровень | Событие |
|---|---|
| `debug` | каждый кадр запроса и каждый кадр ответа, с префиксом `EPP >>` или `EPP <<` |
| `info` | каждый успешный результат — код, `svTRID`, `clTRID` |
| `warning` | каждый неуспешный результат, те же поля |

**Секреты маскируются до того, как кадр попадёт в журнал.** Каждый элемент `<pw>` и `<newPW>`
заменяется на `***` — с любым префиксом пространства имён и любыми атрибутами открывающего тега. Это
покрывает пароль входа, `<newPW>` при смене пароля, `<loginSec:pw>` длинного пароля и `<pw>` внутри
каждого блока `<authInfo>` — то есть код трансфера, единственные учётные данные, позволяющие любому
регистратору забрать у вас домен.

Две вещи, до которых маскирование не дотягивается, потому что это не вывод логгера:

- `Response.raw()` возвращает кадр в том виде, в каком он пришёл, без маскирования. Храните его —
  маскируйте сами.
- Всё, что вы пишете в журнал сами. `authInfo()` возвращает действующие учётные данные: никогда не
  пишите их в журнал, никогда не вкладывайте в обращение в поддержку и меняйте их после того, как
  передали клиенту.

## Транспорт
`Client` общается с внешним миром через интерфейс `com.epptools.sdk.Transport` — `open()`, `isOpen()`,
`writeFrame(String xml)`, `readFrame(): String`, `close()`. Реализация по умолчанию,
`com.epptools.sdk.Connection`, — это TLS-сокет плюс кадрирование по RFC 5734: каждому сообщению предшествует
4-байтовое поле длины в порядке big-endian, **включающее** и сами четыре байта заголовка.

Собственная реализация — это то, чем вы гоняете клиент по записанному обмену в тестах.
`RecordedTransport` здесь — ваш собственный класс, а не класс этой библиотеки: пять методов
поверх того, что вы воспроизводите.

```java
Client client = new Client(config, new RecordedTransport());
```

Два правила, которые соблюдает транспорт по умолчанию и должна соблюдать любая замена:

- Длина кадра меньше 4 байт или больше 1 МиБ отклоняется, а соединение **закрывается**. Байты длины
  к этому моменту уже прочитаны, так что поток стоит на неизвестном смещении.
- Неполное чтение необратимо по той же причине. Продолжив, вы заставили бы следующую команду
  прочитать ответ на текущую — сдвиг на единицу поверх тарифицируемых операций, при котором
  продление возвращает 1000 с датой окончания чужого имени.

Именно поэтому `ConnectionException` посреди команды оставляет результат по-настоящему неизвестным.
Не повторяйте вслепую; см.
[Ошибки](errors.md#когда-трансформирующая-команда-упала-и-вы-не-знаете-выполнилась-ли-она).

## Гигиена сессии

- **По одной команде за раз.** Отправьте команду, прочитайте ответ, затем отправляйте следующую.
  Ради пропускной способности открывайте больше сессий, а не накладывайте команды в одной, и давайте
  каждому потоку собственный клиент.
- **Сессии заканчиваются.** От вашего `logout()`, от тайм-аута простоя, от перезапуска на
  обслуживание. Ничто из того, о чём вам уже сообщили, не теряется: прочитанный вами 1000
  окончателен. Переподключитесь и продолжайте.
- **Следите за лимитом одновременных сессий.** 2502 приходит как `SessionException`; лечится он
  закрытием простаивающей сессии, а не немедленным повтором.
